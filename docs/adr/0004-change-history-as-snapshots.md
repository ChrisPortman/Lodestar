# Change History as state snapshots, not event sourcing

Current state lives in ordinary tables. Every change to any aggregate also writes one row to a single shared Change History table, in the same transaction: entity type and ID, Project ID, the entity version the change produced, `change_kind` (`created` or `updated` only), the Acting Person's ID, a UTC timestamp, full JSON snapshots of the entity `before` and `after` the change, and an optional `caused_by` link to the entry that triggered it (e.g. an unassignment caused by a Member removal). The application layer writes these entries, not database triggers, so it works across databases and records the Acting Person. We rejected event sourcing because the history is for reporting only: it is shown to people but never used to replay or rebuild state, so there is no snapshot schema version. Old entries keep the shape they were written in and are never rewritten. Entries are kept forever.
